# MK LineSim — Engineering Requirements & Risk Register

**Program Phase:** Phase 0, 0.1 & 0.2 (Engineering Baseline, Evidence Reconciliation & Lockfile/CI Hardening)  
**Target System:** MK LineSim (`https://github.com/Minakhairat/MK-LineSim`)  
**Scope:** Formal engineering requirements baseline and classified findings/risk register derived strictly from source inspection and observed command execution (Tasks 6, 8, 12, reconciled in Phase 0.1, lockfile & CI hardened in Phase 0.2).

**Classification Legend (Strict Taxonomy):**
- `Confirmed defect` — Verified mismatch, data corruption/override, or broken engineering/CI guarantee observed directly in source or config.
- `Potential defect` — Latent bug, edge-case inconsistency, or unchecked assumption that triggers under specific valid configurations.
- `Missing verification` — Required engineering behavior, UI path, or regression scenario with zero automated coverage.
- `Design assumption` — Intentional heuristic, fallback, or modeling simplification that must be accepted or governed by V&V acceptance criteria.
- `Verified behavior` — Core capability inspected and verified consistent with unit/regression test execution (`57/57` tests passing).

## 1. Engineering Requirements Baseline (For Phase 1+ V&V)

| Req ID | Domain | Engineering Requirement Statement | Primary Verification Anchor |
| :--- | :--- | :--- | :--- |
| **REQ-CAP-01** | Capacity & Batching | Analytical stage capacity must count only `machine` and `workstation` server capacities (`deduped`), strictly excluding conveyors, buffers, storage, and batch container counts except `collect_batch` cycle amortization. | `capacityEngine.ts:94-210` |
| **REQ-DES-01** | DES Physics & Conservation | Product flow must conserve mass (`Arrived = Good + Scrapped + Active WIP`), prevent physical conveyor overlapping, and respect `bufferCapacity >= 0` blocking backpressure. | `desEngine.ts`, `timeAuditService.ts:189-205` |
| **REQ-DES-02** | Determinism | Identical `ProjectData` (including `randomSeed`) must produce bit-identical `SimulationResult`, event counts, and KPIs across repeated runs. | `desEngine.ts:152,242`, `workerClient.ts` |
| **REQ-OEE-01** | OEE Time Hierarchy | Resource, Stage, and Line time totals must satisfy `CT = PDT + SPT`, `SPT = UDT + SET + OT` (`OT >= 0`), and `OEE = A × P × Q` without double-counting planned downtime, walking, or breakdown repair. | `oeeEngine.ts:4-95`, `resourceStateTracker.ts`, `timeAuditService.ts` |
| **REQ-CAL-01** | Resource Calendars | Resource-specific `shiftId`/`operatingSchedule` and maintenance intervals must govern resource availability without silent fallback on invalid references. | `resourceCalendar.ts:211-240`, `validationEngine.ts:115-143` |
| **REQ-REL-01** | Reliability & Repair | Stochastic failure (`fixed`, `exponential`, `weibull`) and repair (`fixed`, `exponential`, `triangular`, `lognormal`) distributions must reproduce theoretical moments; `availability === 0` must remain continuously unavailable/down. | `failureModels.ts:69-251`, `desEngine.ts:367-408` |
| **REQ-VAL-01** | Input Integrity | Validation must reject non-finite numbers, negative durations, fractional discrete counts (`batchSize`, `capacity`, `requiredWorkers`, `targetQuantity`, `maxPlannedUnits`), calendar overlaps, and physical belt fit violations before execution. | `validator.ts`, `validationEngine.ts` |
| **REQ-CI-01** | Build & CI Reproducibility | Build and CI pipelines must enforce a single canonical lockfile (`package-lock.json` via `npm ci --legacy-peer-deps` without silent `npm install` fallback) and block deployment on `npm run lint` and `npm test` failures. | `package.json`, `package-lock.json`, `.github/workflows/deploy.yml` |
